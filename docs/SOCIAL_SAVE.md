# Social Save
Research and implementation plan • 20 November 2026

An iOS traveler shares a post, reviews named places against a map, keeps the ones they recognize, and finds them again when planning. Nitish selected user-supplied evidence when a URL is insufficient and a signed-in account for every library. Android, messaging bots, bulk import, proximity alerts and pre-trip business status refresh are follow-on releases.

## Delivery plan and acceptance

1. Capture a single source in the iOS share extension or paste form. Keep drafts distinct from pins. Acknowledge persisted intake, including URLs with no extractable text.
2. Bind the library to a verified Supabase user. Isolate rows by auth.uid(), disable anonymous identities, scope REST and MCP to the same owner, and keep demo MCP credentials separate. Provide sign-in, sign-out and deletion.
3. Use fixed-host metadata adapters where allowed. Request a caption, screenshot or video when necessary. Run OCR and speech recognition on supplied content, let the traveler inspect the text and obtain consent before sending it to a model.
4. Extract multiple named places through one bounded endpoint. Accept evidence quotes only when present in the submitted text. Preserve source provenance, creator tips and family observations. Never infer facilities from venue type.
5. Review candidates separately. Search the selected destination in Apple Maps, inspect the match, then confirm. Store user-confirmed labels and place IDs, resolve markers at display time, and handle ambiguous, duplicate and unavailable matches.
6. Organize verified saves by destination. Allow delete, export and must-see locking. Prefer matched saves in planning, carry locks into the schedule, preserve meals, nap windows and geographic constraints, and expose anything that cannot fit.
7. Give signed-in agents a private MCP endpoint for submitting review items and listing confirmed saves. Exercise cross-account reads, updates, deletes and the shared demo token.
8. Evaluate on a family roundup with multiple places, ambiguous branches, a spoken-only name, a sign, a private link and missing family evidence. Track supported precision, recall, incorrect pins, review corrections, lock retention and scheduled saves. Require zero unreviewed pins and zero cross-account reads in release fixtures.
9. Release backend schema and API before the native build. Verify auth email delivery, App Group signing, multiple real host apps, accessibility and deletion on devices. Roll back the client entry point before retiring backend routes. Retain user-owned records across rollback.

## Follow-on validation
Observe families saving during discovery and planning later. Measure the fraction of trips with relevant saves and the fraction of those saves users actually keep in the itinerary. Check place opening status before a trip and pilot on-trip resurfacing only with location permission. Treat Android parity, messaging channels, collaboration, offline access and export promises as separate acceptance tests.

## Developer handoff

Social Save and account features belong to v3. Both repositories use the local branch `feature/v3`. The current app launch uses its existing feature set. Keep the v3 database migration, API deployment and iOS distribution together as a separate release. The server branch starts at web origin/main. The native branch includes build 18's existing age-confirmation and eval-review fixes. Deploy the two together in this order.

1. Apply `src/backend/db/migrations/20261120_037_social_save.sql` to a staging Supabase project. Confirm email auth is enabled and the sign-in and verification templates contain `{{ .Token }}`. Test delivery with a controlled address. The API reads the existing Supabase URL, public anon/publishable key and server-side service key. The service key is used only for account removal after a fresh OTP. [Supabase passwordless email](https://supabase.com/docs/guides/auth/auth-email-passwordless)
2. Deploy the backend to staging. Under `/api/v1/social-save`, GET `/config` returns public sign-in configuration. POST `/extract` accepts an HTTPS source and optional text, returning review candidates or `needs_evidence`. GET/PUT `/places` lists or upserts by account and Apple place ID. GET `/inbox` lists pending imports. Both list endpoints accept an exclusive `after` cursor and return up to 100 records. DELETE `/places/:id` and `/inbox/:id` remove individual records. DELETE `/account` removes the authenticated account following recent OTP verification. Private routes require a user access token.
3. Connect an approved MCP client with the user’s consent. Follow [private MCP account linking](MCP_ACCOUNT_LINKING.md) for the OAuth setup and scoped access to saved places, saved trips and the review inbox. See [the v3 release plan](V3_ACCOUNTS_AND_MCP.md) for account and planning changes.
4. Run `xcodegen generate` in the native repository. Register the share extension identifier `com.sproutroute.app.share` and its existing application group `group.com.sproutroute.app` for distribution. Debug builds accept `SPROUT_API_BASE_URL`. Select a screenshot or a video up to 100 MB and two minutes long. Video OCR samples every three seconds. Local speech recognition depends on device/language support. Reviewers can add or correct text before extraction.
5. Validate the signed app with two accounts, two devices, Apple Maps lookups, a real email code, share sheets from target host apps, sign-out, export, and deletion. Production database changes, distribution signing, email sends and TestFlight release are separate from local validation. Complete the updated App Store privacy declarations alongside release.
6. Run `node scripts/eval-social-save.mjs output.json` with the usual model configuration. The committed synthetic output records one live run. Give the output and the resulting itinerary to a human grader using `docs/benchmarks/social-save-human-grades.csv`, compatible with the existing `score_graders.py`. O1 checks requested saves and locks, O2 checks duplicates/missing days, O5 checks meals/nap/route feasibility, and X2 checks clarity of evidence and correction. Human grades are intentionally blank until someone reviews the result.

The native map uses Apple place IDs. Users can open current place details in Maps. No rating or opening hours are manufactured when a provider omits them. TikTok and YouTube title resolution is best-effort. For Meta links the app retains the link and requests user-supplied evidence instead of extracting Meta embed content. The first release uses evidence-backed family notes and explicit review. Learning from corrections, facility inventories, nearby pairing, notifications and automatic business-status refresh are subsequent work.

## Validation record

On November 20 the Node suite passed 1,114 tests, and the frontend production build passed. A clean snapshot of the native feature branch passed 354 simulator tests. The device Release archive built with signing disabled and contains both the share and widget extensions. Two unrelated Finder metadata files in the working checkout trip its existing clean-tree release test. The clean-snapshot run retained the original test.

The live synthetic family benchmark recovered 12/12 expected place names with zero additional names. It consumed a prepared transcript containing one labeled frame and one labeled audio segment. A separate simulator test exercised Vision on a rendered screenshot. Neither measurement estimates real-reel recall or verifies spoken-only recognition on a physical device. The live fixture also shows why family-note quality needs human grading: named-place recall can pass when a family observation is missed.

The migration ran in a disposable PostgreSQL engine. Independent owner identities, denied cross-account reads/deletes/inserts, and unauthenticated/anonymous access were exercised. Paid extraction, retryable MCP intake, fenced model responses, quote grounding, and preserving negative accessibility evidence have targeted tests. The native suite also covers durable per-owner share intake, must-see placement, protecting meals, and same-name city ambiguity.
