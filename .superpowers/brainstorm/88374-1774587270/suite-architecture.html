Playwright Suite Architecture

How should the test files be structured? Pick the one that feels right.

A

Layered — Tiles → Screens → Flows Recommended

Three layers, each building on the one below. Most granular failures, easiest to debug.

tests/e2e/
├── tiles/
│ ├── hero-tile.spec.ts — destination, dates, kids, country tag
│ ├── weather-tile.spec.ts — forecast days, hi/lo, historical badge
│ ├── itinerary-tile.spec.ts — day tabs, activity cards, meals, warnings
│ ├── safety-tile.spec.ts — advisory, emergency #, health tips
│ ├── map-tile.spec.ts — iframe loads, pin coordinates
│ └── packing-tile.spec.ts — categories, check/uncheck, persistence
├── screens/
│ ├── input-screen.spec.ts — chips, textarea, plan button
│ └── generating-screen.spec.ts — step indicators, progress labels
├── flows/
│ ├── happy-path.spec.ts — full input → results journey
│ ├── destination-picker.spec.ts — vague input → pick → results
│ ├── food-preferences.spec.ts — dietary input → meal cards reflect it
│ └── error-states.spec.ts — 500, 429, empty data
└── smoke/
└── production.spec.ts — live Railway, real APIs
Pinpoints exactly which tile broke Reuses mock fixtures across layers CI runs tiles+screens+flows, skips smoke
B

Flat — Feature files only

Everything at the same level. Simpler but harder to pinpoint failures.

tests/e2e/
├── input-flow.spec.ts
├── results-mosaic.spec.ts
├── itinerary.spec.ts
├── weather.spec.ts
├── packing.spec.ts
├── error-states.spec.ts
└── smoke.spec.ts
Less setup overhead Mixes detailed + flow tests in same file
C

Journey-first — Flows only, no tile isolation

Tests only full user journeys. Fast to write, hard to debug regressions.

tests/e2e/
├── journey-family-beach.spec.ts
├── journey-adults-city.spec.ts
├── journey-vague-input.spec.ts
└── journey-errors.spec.ts
Mirrors how users think One test breaks many things at once

Option A is recommended — it matches your instinct (detailed first, then flows) and makes CI failures self-explanatory. Click to select, then confirm in terminal.
